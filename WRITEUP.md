# Technical Write-up

## 1. Schema Reasoning

The data model was designed to mirror a true multi-tenant SaaS architecture where organizations are the root of the data hierarchy.
- **Organizations**: Represent tenants. They hold a `quota_limit` and `quota_used` for billing/abuse prevention.
- **Users and Org Members**: Users belong to an organization via a bridging table `org_members`, which assigns them a `role` (owner, editor, viewer).
- **Workflows**: Belong directly to an organization (`org_id`). This ensures a clean path for row-level security.
- **Workflow Steps**: A JSONB column `config` was chosen because different node types (`llm_call`, `http_request`, `conditional_branch`) require vastly different payloads. Normalizing this would have created unnecessary complexity.
- **Workflow Runs & Step Runs**: Execution is tracked persistently. `workflow_runs` tracks the overall status (running, paused, completed, failed), while `step_runs` logs the individual execution attempts, inputs, outputs, and errors for observability and resuming.

## 2. The Two Permission Layers

This architecture implements a strict two-layer permission model to ensure both data isolation and operational security.

### Layer 1: Row-Level Security (RLS) via Hasura
The first layer is enforced directly at the database level by Hasura's GraphQL Engine. 
We configured Hasura permissions so that a user cannot even query or mutate a workflow unless they are an active member of that workflow's organization. 
- **Enforcement Mechanism**: Hasura uses session variables (e.g., `x-hasura-user-id`) provided by the Nhost auth JWT. 
- **Isolation**: A user in `Org B` cannot guess the ID of a workflow in `Org A` because the Postgres query generated by Hasura automatically appends a `WHERE org_id IN (SELECT org_id FROM org_members WHERE user_id = $x-hasura-user-id)`. This makes direct ID guessing physically impossible.

### Layer 2: Backend Executor Gating (Actions)
The second layer governs *what* a user can do with their access, specifically regarding potentially dangerous workflow nodes (like `db_write` or `webhook`).
- **Enforcement Mechanism**: This cannot be handled by a simple database RLS read/write rule because it is an operational execution rule. Instead, this is enforced inside the Next.js API route that handles the Hasura Action (`triggerWorkflowRun` and `approveStep`).
- **Validation**: Before the executor spins up the pipeline, it queries the `org_members` table on the backend (using a service role or verifying the user's JWT) to check if the caller is an `owner`. If a `viewer` tries to trigger a run via the API, the backend throws an error.

## 3. Approval Gate Implementation

The `approval_gate` node presents a unique distributed systems challenge: pausing an asynchronous execution pipeline and cleanly resuming it from an external trigger.

### Pausing
When the custom Execution Engine evaluates a workflow and encounters an `approval_gate` step type:
1. It immediately updates the `step_run` status to `PENDING_APPROVAL`.
2. It updates the parent `workflow_run` status to `PAUSED`.
3. **The execution loop terminates.** The function ends entirely. We do not use long-polling or `setTimeout` delays which would exhaust serverless function limits.

### Resuming
The frontend UI subscribes to `step_runs` via GraphQL subscriptions. When a step turns to `PENDING_APPROVAL`, it renders an "Approve/Reject" UI.
1. When an authorized user clicks "Approve", the frontend calls the `approveStep` Hasura Action.
2. The Action handler (in Next.js) verifies that the caller is an `owner` or `editor` in that organization (Layer 2 gating).
3. If authorized, the backend marks the `step_run` as `COMPLETED` and updates the `workflow_run` back to `RUNNING`.
4. It then recursively invokes the core execution engine again, passing in the remaining steps, picking up exactly where it left off!
